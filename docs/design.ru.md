# Заметки о дизайне pack-sync

> Исходная спецификация от 2026-11-10 и то, что выяснилось при реализации, для сервера автора.
> Пути в ней указаны на тот момент: тогда код жил в `tools/pack-sync` репозитория сайта. Актуальная
> документация: [README](../README.md), [owner-guide](owner-guide.md), [security](security.md).


Утверждено 2026-11-10.

## Цель

Игрок и сервер всегда на одной свежей версии модов, игроку ничего не нужно ставить руками.

## Что это такое

Маленькая программа на Rust `pack-sync`, которая запускается до игры. Обычный мод не подходит:
моды Horizon вкомпилированы в движок, и запущенная игра не может заменить сама себя.

## Как идёт обновление

1. Новая версия мода выходит в его публичном репозитории.
2. Команда `publish` на ПК собирает клиент под Windows и сервер под Linux (в Docker), подписывает
   манифест и выкладывает релиз в приватный репозиторий сборки.
3. Сервер раз в несколько минут спрашивает сайт о новой версии. Найдя её, предупреждает игроков в
   чате, ставит новый движок и перезапускается. Если игра не поднялась, откатывается.
4. После успешного запуска сервер сообщает сайту свою версию.
5. Клиент при запуске получает версию, на которой уже работает сервер, поэтому не окажется новее
   сервера.

## Ключевые решения

- Токен GitHub хранится только на сайте. За файлом сайт отдаёт клиенту временную ссылку GitHub,
  поэтому тяжёлый трафик через сервер сайта не идёт.
- Доступ к сборке даётся по личному коду из профиля на сайте, код можно отозвать.
- Подпись ed25519: закрытый ключ только у владельца, открытый вшит в `pack-sync`. Неподписанное не
  ставится даже при взломе GitHub или сайта.
- Если сайт недоступен или подпись неверна, игра запускается на текущей версии, причина пишется в
  лог.
- Первая установка: игрок один раз запускает установщик, вводит код и соглашается на автообновления.

## Части работы

`pack-sync` (клиент и сервер), команда `publish`, три адреса на сайте и таблица кодов, установщик,
системная служба на сервере.

## Ограничения

- Новая версия мода попадает в сборку только после запуска `publish`.
- Игрок, который уже в игре, получает обновление при следующем запуске.

## Готово, когда

На тестовом сервере и тестовом профиле выпуск новой версии доходит до обоих без ручных действий,
подделанная сборка отклоняется, а сломанная откатывается.

## Что выяснилось при реализации

- Лаунчер запускает `cmd /C "<команда> && <путь к игре>"`, то есть путь к игре известен до команды,
  и свежий `import-build` сработал бы только со следующего запуска. На Windows лаунчер к тому же
  копирует игру в слот `run\<хеш>\game` и запускает копию, а файл в папке версии держит открытым до
  выхода из игры. Поэтому `pack-sync` хранит текущую сборку у себя (`builds\<номер>`) и перед каждым
  запуском кладёт её в слот, путь к которому лаунчер передаёт в `HORIZON_WINDOWS_RUNTIME_SLOT`. Без
  слота файл игры заменяется в папке версии. Если у сборки другая база Horizon, нужны новые файлы игры: установка идёт
  через `import-build`, а игрока просят нажать «Играть» ещё раз.
- Архив сервера содержит ресурсы, полученные из файлов игры, поэтому сайт отдаёт игрокам только
  файлы `client-*`.
- Флаг `--trust-native-code` фиксирует решение человека. По правилам Horizon агент его не
  подставляет, поэтому `publish.ps1` требует, чтобы владелец передал `-TrustNativeCode` сам.
- Подготовленные файлы игры передаются в контейнер Linux с ПК владельца: для их подготовки внутри
  контейнера нужен вход в аккаунт.
